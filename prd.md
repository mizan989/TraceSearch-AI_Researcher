### Product Summary

TraceSearch is an AI-powered research engine designed to help users
move from a question to a structured, source-traceable research result.

Unlike a conventional AI chatbot that primarily provides a
conversational answer, TraceSearch is designed around the research
workflow:

**Ask → Search → Collect → Analyze → Trace → Synthesize → Explore**

The product will use SerpApi to retrieve web search results and Gemini
to analyze and synthesize the retrieved information. The system will
preserve source attribution so users can inspect where important
findings came from.

### Product Principle

> **Search. Analyze. Trace.**

The product should optimize for **useful research and source
transparency**, not simply for producing a fluent AI answer.

# 2. Problem Statement / Context

## 2.1 Problem

People frequently use search engines and AI assistants together when
researching a topic.

A typical workflow looks like:

1.  Search Google.
2.  Open multiple results.
3.  Read several pages.
4.  Compare conflicting information.
5.  Copy important facts into notes.
6.  Ask an AI assistant to summarize the information.
7.  Return to the original sources to verify claims.
8.  Repeat the process when information is incomplete or contradictory.

This creates several problems:

-   Research is fragmented across tabs and applications.
-   Users spend time deciding which sources are relevant.
-   AI-generated answers can obscure the relationship between claims and
    sources.
-   Comparing several sources manually is time-consuming.
-   Users may have difficulty identifying conflicting information.
-   Research results are difficult to preserve as a reusable artifact.
-   Repeating research for a different topic requires starting over.

## 2.2 Why It Is Worth Solving

The value proposition is not simply "AI can answer questions."
General-purpose AI assistants already provide conversational answers.

TraceSearch instead focuses on the **research process and evidence
trail**.

The product should make it easier for a user to answer:

-   What did the web say?
-   Which sources support this finding?
-   Are multiple sources saying the same thing?
-   Are there conflicting claims?
-   What information is missing?
-   Can I inspect the original source?
-   Can I preserve or share my research?

## 2.3 Hackathon Context

The first release is a hackathon MVP. The goal is to demonstrate a
compelling end-to-end research workflow rather than build a complete
production-scale search platform.

The MVP should therefore prioritize:

1.  A polished research experience.
2.  Reliable retrieval of web search results.
3.  Useful AI synthesis.
4.  Visible source attribution.
5.  A clear demonstration of claim-to-source traceability.
6.  Fast enough interaction for a live demo.

The MVP should avoid spending hackathon time on features that do not
materially improve the core research workflow.

# 3. Goals & Success Metrics

## 3.1 Product Goals

### Goal 1 --- Reduce research friction

Allow a user to enter a research question and receive a structured
starting point without manually opening numerous search results.

### Goal 2 --- Make sources visible

visible relationship to one or more retrieved sources wherever
technically possible.

Turn a search session into a structured research artifact containing:

-   Summary
-   Key findings
-   Sources
-   Evidence
-   Related information
-   Follow-up questions

### Goal 4 --- Demonstrate intelligent synthesis

Use Gemini to synthesize retrieved information rather than simply
returning raw search results.

The complete core workflow should work reliably from a fresh deployment.

# 5. User Stories & Functional Requirements

## 5.1 MoSCoW Prioritization

### Must Have

These are required for the hackathon MVP.

#### M1 --- Research Query

**User story:**\
As a user, I want to enter a natural-language research question so that
I can start an investigation.

**Requirements:**

-   Provide a prominent search/research input.
-   Support natural-language questions.
-   Allow submission using a button and Enter key.
-   Display the submitted query clearly.
-   Validate empty or excessively long queries.

------------------------------------------------------------------------

#### M2 --- Web Search Through SerpApi

**User story:**\
As a user, I want TraceSearch to retrieve current web information
relevant to my question.

**Requirements:**

-   Backend sends search requests to SerpApi.
-   Search queries should be generated from the user's research
    question.
-   The backend must keep API credentials server-side.
-   Search results should include available title, URL, snippet, and
    source metadata.
-   The application should handle API errors gracefully.
-   Search results should be normalized into a consistent internal
    schema.

------------------------------------------------------------------------

#### M3 --- AI Research Synthesis

**User story:**\
As a user, I want the application to analyze retrieved sources and
produce a useful research response.

**Requirements:**

-   Send relevant search information to Gemini.
-   Generate a structured response.
-   Avoid presenting unsupported information as sourced fact.
-   Clearly distinguish sourced findings from AI-generated
    interpretation where practical.
-   Handle cases where search results are insufficient.

------------------------------------------------------------------------

#### M4 --- Source Display

**User story:**\
As a user, I want to see the sources used in my research.

**Requirements:**

-   Display source title.
-   Display source domain.
-   Provide a clickable source link.
-   Display sources near relevant findings when possible.
-   Provide a consolidated source section.

------------------------------------------------------------------------

#### M5 --- Claim / Evidence Traceability

**User story:**\
As a user, I want to understand where important findings came from.

**Requirements:**

-   Major findings should reference one or more sources.
-   Source references should be visually identifiable.
-   Clicking a citation should reveal or navigate to the relevant
    source.
-   The UI should avoid implying that a source supports a claim when the
    relationship has not been established.
-   If evidence cannot be confidently associated, the UI should label
    the information accordingly.

------------------------------------------------------------------------

#### M6 --- Structured Research Report

The response should be organized into sections such as:

1.  Executive summary.
2.  Key findings.
3.  Evidence / supporting sources.
4.  Important details.
5.  Contradictions or uncertainty where detected.
6.  Sources.
7.  Suggested follow-up questions.

------------------------------------------------------------------------

#### M7 --- Loading and Progress States

The application should communicate what is happening during research.

Example:

``` text
Understanding your question...
↓
Generating research queries...
↓
Searching the web...
↓
Analyzing sources...
↓
Building your report...
```

------------------------------------------------------------------------

#### M8 --- Error Handling

The system must handle:

-   Invalid query.
-   SerpApi failure.
-   Gemini failure.
-   Rate limit.
-   Timeout.
-   Empty search results.
-   Malformed source data.
-   Network failure.

Users should receive understandable messages rather than raw stack
traces.

------------------------------------------------------------------------

### Should Have

#### S1 --- Multi-Query Research

Generate 2--3 complementary searches from one user question.

Example:

User query:

> "What is the future of EVs in India?"

Possible searches:

-   India EV market 2026.
-   India EV adoption trends.
-   India EV policy and incentives.

The system should avoid unnecessarily duplicating queries.

------------------------------------------------------------------------

#### S2 --- Source Categorization

Classify sources into categories such as:

-   Official
-   News
-   Academic / research
-   Company
-   Technical documentation
-   Blog
-   Community
-   Other

This classification is an application-level categorization and should
not be represented as an objective measure of source quality.

------------------------------------------------------------------------

#### S3 --- Follow-Up Questions

After producing a report, suggest questions such as:

-   "What are the biggest risks?"
-   "Compare the main companies."
-   "Show the evidence for this finding."
-   "What changed during the last year?"

Selecting a follow-up should start a new research operation while
preserving context.

------------------------------------------------------------------------

#### S4 --- Research History

Store previous research sessions for authenticated users.

Each history item should include:

-   Query.
-   Date/time.
-   Research status.
-   Short summary.
-   Number of sources.

------------------------------------------------------------------------

#### S5 --- Shareable Research URL

Allow users to generate a read-only URL for a completed research report.

------------------------------------------------------------------------

#### S6 --- Responsive Design

The application should work on desktop, tablet, and mobile browsers.

------------------------------------------------------------------------

### Could Have

#### C1 --- Deep Research Mode

A more extensive workflow that performs additional searches based on
information gaps discovered during initial research.

------------------------------------------------------------------------

#### C2 --- Evidence Map

A visual representation:

``` text
Finding A
 ├── Source 1
 ├── Source 2
 └── Source 3

Finding B
 ├── Source 2
 └── Source 4
```

------------------------------------------------------------------------

#### C3 --- Contradiction Detection

Identify potentially conflicting statements across retrieved sources.

The product should say that sources **appear to disagree** rather than
declaring one source correct without sufficient evidence.

------------------------------------------------------------------------

#### C4 --- PDF Export

Export the completed research report as a formatted PDF.

------------------------------------------------------------------------

#### C5 --- Research Collections

Allow users to save multiple reports into named collections.

------------------------------------------------------------------------

#### C6 --- Query Suggestions

Suggest improved or narrower research questions before searching.

------------------------------------------------------------------------

### Won't Have --- Current Release

#### W1 --- Autonomous unrestricted browsing

The MVP will not build a general-purpose browser agent that can browse
arbitrary websites indefinitely.

#### W2 --- Full enterprise collaboration

No enterprise permissions, team administration, SSO, audit logs, or
advanced workspace management.

#### W3 --- Native mobile applications

No dedicated Android/iOS application for the MVP.

#### W4 --- Training a proprietary LLM

The project will use an external LLM API rather than training a
foundation model.

#### W5 --- Guaranteed factual correctness

TraceSearch will not claim that every generated statement is
objectively true. The system will provide source visibility and
uncertainty indicators where appropriate.

# 7. Non-Functional Requirements (NFRs)

## 7.1 Performance

### NFR-P1 --- First Feedback

The application should show a loading/progress state within **1 second**
of a valid request under normal conditions.

### NFR-P2 --- First Useful Output

Target median time to first meaningful research output: **≤ 10
seconds**.

### NFR-P3 --- Complete Research

Target median completion time for standard research: **≤ 30 seconds**.

Actual performance will depend on SerpApi, Gemini, network conditions,
query complexity, and deployment region.

### NFR-P4 --- Frontend Performance

Target:

-   Responsive interaction.
-   Minimal blocking JavaScript.
-   Optimized images.
-   Lazy loading where appropriate.

------------------------------------------------------------------------

## 7.2 Scalability

The architecture should allow the search and AI providers to be replaced
without rewriting the frontend.

Recommended abstraction:

``` text
SearchProvider
 └── SerpApiProvider

LLMProvider
 └── GeminiProvider
```

This allows future providers to be introduced without tightly coupling
application logic to one vendor.

The MVP should support at least the expected concurrent traffic for a
hackathon demo without obvious failures.

------------------------------------------------------------------------

## 7.3 Security

### API Keys

-   Never expose SerpApi or Gemini API keys to the browser.
-   Store secrets in deployment environment variables.
-   Never commit secrets to Git.

### Authentication

If accounts are implemented:

-   Use a trusted authentication provider.
-   Protect private research history.
-   Enforce server-side authorization.

### Input Security

-   Validate and sanitize user input.
-   Protect against prompt injection where external web content is
    passed to the LLM.
-   Treat retrieved web content as untrusted data.
-   Do not allow retrieved content to override system/application
    instructions.

### External Links

-   Clearly identify external source links.
-   Avoid embedding untrusted pages directly where unnecessary.

### Data Privacy

The application should minimize storage of user queries and research
content.

If research history is stored, the product should clearly communicate
what is stored and why.

------------------------------------------------------------------------

## 7.4 Reliability

The system should degrade gracefully.

Example:

``` text
SerpApi unavailable
      ↓
Show error
      ↓
Preserve user's query
      ↓
Allow retry
```

Gemini unavailable:

``` text
Search succeeded
      ↓
AI synthesis failed
      ↓
Show retrieved sources
      ↓
Allow retry
```

The user should not lose their query because one downstream service
fails.

------------------------------------------------------------------------

## 7.5 Observability

For the MVP, log:

-   Request ID.
-   Timestamp.
-   Search success/failure.
-   LLM success/failure.
-   Response latency.
-   Number of search queries.
-   Number of sources returned.
-   Error category.

Do not log sensitive user information unnecessarily.

# 9. Assumptions, Risks & Dependencies

## 9.1 Assumptions

### A1 --- Search API availability

SerpApi will provide sufficient search access for hackathon development
and demonstration.

### A2 --- LLM availability

Gemini API access and available quota will be sufficient for the planned
demo workload.

### A3 --- Web results contain enough information

Search snippets and accessible metadata will often provide enough
information for an initial research synthesis.

### A4 --- Users value traceability

The product assumes that users benefit from being able to inspect
sources behind AI-generated findings.

### A5 --- Hackathon traffic is limited

The initial architecture is designed for a demonstration/MVP rather than
mass consumer traffic.

------------------------------------------------------------------------

## 9.2 Risks

### R1 --- API quota exhaustion

Multiple searches per research request can consume the SerpApi quota
quickly.

**Mitigation:**

-   Limit searches per request.
-   Cache repeated queries.
-   Prevent duplicate searches.
-   Display usage monitoring during development.

------------------------------------------------------------------------

### R2 --- LLM API limits

Gemini rate limits could cause failures during a live demo.

**Mitigation:**

-   Use concise prompts.
-   Limit source content sent to the LLM.
-   Implement retries with backoff.
-   Prepare fallback demo queries.
-   Monitor quota before presentation.

------------------------------------------------------------------------

### R3 --- Hallucination

Gemini may generate unsupported or incorrect information.

**Mitigation:**

-   Provide source context.
-   Require citations.
-   Instruct the model to identify uncertainty.
-   Avoid unsupported claims.
-   Provide direct source access.

------------------------------------------------------------------------

### R4 --- Source quality variation

Search results can include outdated, low-quality, or irrelevant pages.

**Mitigation:**

-   Retrieve multiple sources.
-   Categorize sources.
-   Prefer relevant and authoritative sources where detectable.
-   Show source metadata.
-   Allow users to inspect original pages.

------------------------------------------------------------------------

### R5 --- Prompt Injection Through Web Content

A retrieved page may contain malicious instructions designed to
manipulate an LLM.

**Mitigation:**

-   Treat web content as untrusted.
-   Separate system instructions from retrieved content.
-   Explicitly instruct the LLM that retrieved text is evidence, not
    instructions.
-   Limit tools available to the model.

------------------------------------------------------------------------

### R6 --- Slow research response

Sequential searches and AI calls could make the application feel slow.

**Mitigation:**

-   Parallelize independent searches.
-   Stream UI progress.
-   Cache results where appropriate.
-   Limit search count for standard mode.

------------------------------------------------------------------------

### R7 --- Hackathon demo failure

External API outages or rate limits could break the demonstration.

**Mitigation:**

-   Prepare a controlled demo dataset/cache.
-   Have several pre-tested queries.
-   Implement graceful fallback behavior.
-   Keep the live architecture functional while allowing demo-safe
    cached results if necessary.

------------------------------------------------------------------------

# 11. AI Requirements

## 11.1 Research Planner

The system should convert a broad question into a small set of
complementary search queries.

Example:

**Input**

> "How is AI changing software development?"

**Generated searches**

1.  AI software development productivity studies.
2.  AI coding assistants developer adoption.
3.  AI impact software engineering jobs.

The planner should avoid generating redundant searches.

------------------------------------------------------------------------

## 11.2 Synthesis

The LLM should:

-   Summarize retrieved evidence.
-   Identify major themes.
-   Attribute claims to sources.
-   Identify uncertainty.
-   Avoid inventing citations.
-   Avoid claiming that a source says something it does not.
-   Prefer information supported by multiple relevant sources when
    available.

------------------------------------------------------------------------

## 11.3 Structured Output

The LLM should ideally return a predictable schema such as:

``` json
{
  "title": "Research title",
  "summary": "Executive summary",
  "findings": [
    {
      "title": "Finding title",
      "content": "Finding explanation",
      "source_ids": ["source_1", "source_3"]
    }
  ],
  "uncertainties": [],
  "follow_up_questions": []
}
```

The backend should validate this output before sending it to the
frontend.

# 14. Definition of Done

The TraceSearch MVP is considered complete when:

-   [ ] A user can open the deployed application.
-   [ ] A user can submit a research question.
-   [ ] The backend generates relevant search queries.
-   [ ] SerpApi successfully retrieves web results.
-   [ ] The system presents a research progress state.
-   [ ] Gemini produces a structured synthesis.
-   [ ] The final response contains key findings.
-   [ ] Findings have source references where applicable.
-   [ ] Users can inspect and open the original sources.
-   [ ] API failures produce understandable error states.
-   [ ] API keys are not exposed client-side.
-   [ ] The application works on desktop and mobile layouts.
-   [ ] At least three representative research queries have been tested
    end-to-end.
-   [ ] The application can be demonstrated reliably from a fresh
    session.
-   [ ] The deployed URL is publicly accessible to the judging team.

# 17. Product Positioning

## One-Line Description

**TraceSearch is an AI-powered research engine that searches the web,
synthesizes information, and lets users trace important findings back to
their sources.**

## Short Pitch

> **Search. Analyze. Trace.**
>
> TraceSearch turns a question into a structured research report by
> searching the web, analyzing multiple sources with AI, and connecting
> important findings back to their evidence.

## Core Differentiator

TraceSearch should not compete primarily on being another
conversational AI.

Its differentiator is the **research workflow + source traceability**:

``` text
Traditional AI

Question
   ↓
Answer


TraceSearch

Question
   ↓
Research
   ↓
Sources
   ↓
Evidence
   ↓
Analysis
   ↓
Traceable Answer
```

# 18. Appendix --- Initial Product Vocabulary

  -----------------------------------------------------------------------
  Term                                Definition
  ----------------------------------- -----------------------------------
  **Research Session**                One complete user research task
                                      from query submission to generated
                                      report

  **Research Query**                  A search query generated from or
                                      supplied by the user

  **Source**                          A web result retrieved during
                                      research

  **Finding**                         A significant piece of information
                                      presented in the final report

  **Evidence**                        Source information supporting a
                                      finding

  **Trace**                           The relationship between a finding
                                      and its supporting source(s)

  **Research Planner**                Component that decomposes a user
                                      question into search queries

  **Synthesis**                       AI-generated combination and
                                      explanation of retrieved
                                      information

  **Deep Research**                   Extended research workflow
                                      involving additional searches and
                                      analysis

  **Source Categorization**           Application-level classification of
                                      sources by type
